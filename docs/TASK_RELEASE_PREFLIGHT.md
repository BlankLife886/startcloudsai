## 当前发布流程的关键问题

### Candidate 与生产共享数据

`deploy/docker-compose.candidate.yml` 复用生产 data/outbound 网络，并读取发布目录的 `.env`；一体化 candidate 则明确连接正式 PostgreSQL、Redis、Web、Admin 和 ChatGPT2API。

`runServe` 在提供 HTTP 服务前自动执行数据库迁移、内置内容补齐和存储配置密钥加密。因此，即使只启动 candidate 并查看健康接口，也可能已经写入生产数据库。它属于生产切流设施，不能作为可随意创建、重试、取消任务的隔离测试环境。

实际预发布应有独立数据库、Redis、对象存储资源及明确的上游测试配置。当前仓库没有提供可确认的独立预发布访问地址，本轮未把生产 candidate 当作替代。

### 旧 API-only 脚本不适用于本次更新

`deploy/integrated/scripts/deploy-backend-release.sh` 明确只更新 API，保留旧 Worker。一体化迁移说明中也保留了同样步骤。

本次新增 `assistant-chat`、`assistant-image` 执行队列、统一按张计量和私有执行快照，必须同步安排 API、Worker 及客户端版本。旧 Worker 不会消费新助手队列，普通任务混跑新旧 Worker 时也可能使用不同的准入及配置读取规则。

`deploy-app-update.sh` 会更新所有应用服务，但仍不能直接视为本次发布已具备充分保护：

- 两次检查活动任务数量之后，公网仍可接收新请求；任务可能在最后一次检查与替换服务之间进入。
- API 替换在 Worker 之前，仍有新 API 与旧 Worker 共存的窗口。
- Worker 就绪检查只匹配 `worker ready` 日志，而该日志早于独立对话执行池启动，不能证明两类队列均已有消费者。

本轮对这些脚本只做了检查，没有执行或改变它们的生产行为。本次发布应按下列受控步骤安排，不能直接照搬 API-only 路径。

### 修复尚未进入已提交发布包

当前工作区仍有修改及未跟踪的新文件，包括 `00145_execution_snapshots.sql`。现有发布说明使用 `git archive` 按提交打包，这不会包含未提交修改。发布前必须先核对并提交本次完整变更，生成对应提交的发布包和校验值，避免只发布到部分修复。

## 超时与 nginx HTML 的判断

| 层级 | 仓库配置 | 对本次判断的意义 |
| --- | --- | --- |
| 宝塔入口示例 | connect 60 秒；read/send 600 秒；关闭响应缓冲 | 只是仓库示例，尚未读取服务器的实际生效配置 |
| Docker Gateway | API read 300 秒；助手关闭缓冲；任务 SSE 通过上游响应头关闭缓冲 | 最先达到的代理空闲超时会影响请求；外层 600 秒不能覆盖内层 300 秒 |
| Go API | ReadHeader 10 秒；Read 30 秒；Write 310 秒 | SSE 的 Go 写超时还需要长连接/自动重连场景核验，不能只看 Nginx 心跳 |
| SSE | 每 15 秒心跳 | 隔离检查证明流式响应可穿过 Gateway 并通过心跳维持空闲连接；没有在本轮实际等待 310 秒 |

已复现两条 HTML 路径：

1. 合成 API 在 Gateway 空闲期限内不返回响应头，Gateway 返回自己的 `504 Gateway Time-out` HTML，错误日志出现等待上游响应头超时。
2. 合成上游直接返回 504 HTML，Gateway 转发该状态和正文。

这解释了为什么不能仅凭页面上出现 nginx 字样定位故障层级。以前那次线上错误的具体来源，仍需对应时间、请求路径、request ID、任务 ID、宝塔/Gateway 错误日志及 Worker 上游记录，不能用本地复现代替现场证据。

## 本次建议的受控切换顺序

以下是待实际环境核验后的操作顺序，本轮没有执行：

1. 确定部署拓扑、当前提交/镜像 ID、数据库迁移版本；核对 API 和 Worker 使用一致的 `APP_SECRET`，比较指纹而不输出密钥。准备完整发布包、旧镜像和可验证备份。
2. 在真正隔离的预发布环境应用完整迁移，部署同一提交的 API、Worker、Web、Admin，核验本次任务链路及实际代理配置。
3. 正式切换窗口内，暂停新任务提交，确保覆盖助手、普通任务、电商批次、画布及开放 API；保留状态查询、事件订阅和必要内部回调。仅检查一次“当前为零”不足以关闭新请求进入的窗口。
4. 等待已接收任务结束，并核对活动任务、上游待处理尝试及队列状态。不以强制失败或删除队列代替正常排空。
5. 在提交入口仍暂停的情况下停止旧 Worker 领取新任务，再启动新 API 完成迁移，随后启动匹配版本 Worker。新 API 健康不代表新 Worker 就绪。
6. 核验普通图片与独立聊天的实际队列消费者、两类资源指标及版本；更新匹配的 Web/Admin，最后恢复新任务提交。
7. 观察排队时长、成功率、重复提交、退款和遗留冻结。回滚前核对旧代码是否理解新队列及新写入记录；不能只回滚 API，或用数据库回退掩盖已产生的新账务数据。

该顺序采用受控提交窗口，不承诺零停机。具体入口暂停方式、排空标准、回滚边界及允许的真实测试调用，应在目标环境明确后再执行。
