# 大数据量后台列表查询

## 本次覆盖

| 页面 | 服务端筛选 | 浏览方式 |
| --- | --- | --- |
| 任务与调度 | 创建日期、任务 ID / 提示词关键词、用户 ID / 邮箱 / 用户名、任务类型、状态、错误码 | 默认近 30 天，游标分页；清空日期可查历史 |
| 用户管理 | 注册日期、用户 ID / 邮箱 / 用户名、账户状态、生命周期、风险、画像标签 | 页码分页，列表和总数使用同一条件 |
| 操作审计 | 操作日期、管理员邮箱、请求路径、HTTP 方法 | 游标分页 |
| 兑换码 | 生成日期、完整兑换码、批次、状态 | 游标分页 |
| 订单 | 已有创建日期、搜索、用户、套餐、订单类型、状态、支付方式、退款、交付、金额区间 | 保留现有服务端查询与汇总 |
| 提示词 / 社区 / 投稿 | 已有服务端关键词、分类或类型、状态等筛选 | 保留分页或按需加载；不是把全部记录传到浏览器再搜索 |

时间选择统一按北京时间自然日：包含开始日期和结束日期全天。快捷项为今天、近 7 / 30 / 90 天。切换条件从第一页重新读取；任务页“重置为近30天”会恢复默认时间窗口。

## 推荐查找方式

先缩小时间范围，再选类型 / 分类和状态，最后输入关键词。知道完整用户 ID 或任务 ID 时优先按 ID 查询。查旧任务时记得调整或清空默认的近 30 天范围。任务列表、状态统计和清空记录共享筛选条件，筛选未加载完成时不可执行清空。

用户查询不再把 UUID 当作邮箱片段；任务按用户搜索改为数据库关联查询，避免原先最多匹配 200 个用户造成漏查。`%` 和 `_` 在新增任务关键词及用户搜索中按普通字符匹配。

## 分页与容量边界

- 浏览器只拿当前页或用户主动追加的页面，不需要一次加载 20 万条记录。
- 游标接口不能直接计算任意远页的起始位置。已访问页可直接访问；一次跳转若需要额外遍历超过 20 页，会明确要求缩小筛选范围，避免发送数千次请求。
- 任务与调度支持页码跳转：请求带 `page` 时，服务端先用轻量列定位目标页的排他起点（响应返回 `cursor`），再按游标取页，一次请求完成；总页数取自当前状态标签的计数。与其他页码分页一样只能浏览前 10000 条，更早的任务请用创建日期筛选。
- 用户页和用户端钱包账本使用服务端页码查询，只能浏览筛选结果的前 10000 条（`store.ListCountCap`），超出时返回 422 并提示缩小筛选范围。
- 用户列表、钱包账本总数和任务状态统计为带上限计数：最多统计 10000 条，超过时 `total` 为 10000、`totalCapped=true`（任务统计为 `capped.<字段>=true`），界面显示"10000+"。计数成本因此与历史总量无关。
- 游标条件使用行值比较 `(created_at, id) < ($1, $2)`，可直接作为 `(created_at DESC, id DESC)` 索引的范围条件；任务列表的 `tasks` + `assistant_runs` UNION 在每个分支内排序截断后再合并。翻页成本与深度无关。
- 用户列表不再在请求内同步计算缺失的用户画像，改为加入 `user_profile_refresh_queue`，由 Worker 每分钟刷新；新用户首次出现时画像列可能短暂为空。
- 反馈、体验申请、提示词排序、订单、用户详情的账本与任务同样支持页码跳转（`?page=N`，服务端回显 `page`）；超过 10000 条的部分请缩小筛选范围。服务端未按页码返回时前端退回逐页游标，不会显示错位数据。
- 后台游标附带筛选哈希（`<游标>.<哈希>`），换了筛选条件却沿用旧游标会返回 422，而不是错位的数据；翻页位置、页大小和 `summary` 不参与哈希。用户端与 App 的游标不做绑定。
- 提示词库按热度或手动排序时，游标记录游标行的排序值；游标行被删除或计数变化不会让下一页变空或错位。其他条目在翻页期间计数变化仍可能导致轻微跳动，这是按可变数值排序的固有限制。
- 好友拼团、安全中心风险事件、文件哈希规则、支付对账改为服务端页码分页并返回带上限总数；兑换码批次选择框默认列出最新 50 个批次，可按批次号或备注远程搜索。
- 订单列表的金额汇总只在筛选条件变化时计算（翻页请求带 `summary=false`）；列表 `total` 封顶 10000，精确数量见 `summary.total`。
- 保留期限由管理员在「系统设置 → 运行日志」配置：平台日志默认 7 天（1-90 天，另有容量上限），后台操作审计默认 180 天（7-365 天），Worker 每小时删除超期记录。调低后下一次清理即删除超期数据，无法恢复。
- 电商商品库按创建时间倒序分页（此前按最近编辑），翻页期间被编辑的商品不会再被跳过。
- 模型、公告、服务商等配置列表仍使用前端分页，适用于小规模配置，不能据此推断所有模块都支持几十万条配置。
- 总数统计、大范围模糊匹配、批量清理与导出仍可能耗时；大量删除或导出应该分范围执行。未来更大规模时需要单独评估异步批处理、报表缓存与归档策略。

## 数据库变更及验证

迁移 `00156_admin_list_search_indexes.sql` 使用并发建索引，补充用户时间 / 状态、邮箱和用户名模糊搜索、任务类型 / 提示词、审计方法和兑换码状态索引。邮箱为 `citext`，查询与索引显式使用 `email::text`，避免无法命中 trigram 索引。迁移尚需随发布执行；仅更新前端不会获得数据库索引收益。

本地 PostgreSQL 独立临时库测试了 20 万条合成用户数据。针对高选择性的邮箱关键词，调整前“计数 + 首屏”约 135 ms，调整后约 33 ms；后者的 EXPLAIN 确认使用邮箱和用户名的 Bitmap Index Scan。该结果只代表此本地合成查询，不是所有页面、所有关键词或生产并发下的性能承诺。仍需在真实数据分布下检查 EXPLAIN (ANALYZE, BUFFERS)、慢查询、CPU、数据库连接和接口 P95。

测试入口：

```sh
# 仅在本地独立临时数据库中生成并清理测试数据
cd apps/server
TEST_DATABASE_URL=postgres://localhost:5432/postgres ADMIN_LIST_PERF_ROWS=200000 \
  go test ./internal/store -run '^TestAdminListLargeDataset$' -count=1 -v
```
