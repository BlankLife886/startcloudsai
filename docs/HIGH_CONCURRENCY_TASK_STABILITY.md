# 高并发任务稳定性方案

本文定义用户连续创建几十到一百个图片任务时的调度、状态同步、失败恢复和容量边界。目标不是让一百个请求同时打向上游，而是允许用户快速提交工作，由平台平稳排队，并保证切换页面、网络波动或 Worker 重启后仍能回收结果。

## 核心不变量

1. 一个业务任务只冻结一次费用、只使用一个稳定任务 ID。
2. 页面卸载不会取消服务端任务，上游结果由 Worker 持久化到 R2 和数据库。
3. 客户端等待任务数增加时，连接数和轮询请求数不线性增长。
4. Worker 并发始终小于用户可排队数量，突发流量通过队列吸收。
5. 上游超时不能立即等价为生成失败；具备幂等 ID 的任务必须先尝试恢复。
6. 恢复任务有次数、批量和时间边界，不能形成无限重试或重复队列记录。

## 前端调度算法

### 提交窗口

`tasksApi.createTask` 使用全局 FIFO 信号量，浏览器同时最多执行 6 个任务创建请求。用户快速点击产生的其余请求在内存队列中等待；页面上的本地任务卡片仍立即创建，因此点击不会失去反馈。

提交请求携带 `idempotencyKey`。单次创建请求最多占用网络槽位 30 秒；网络错误、超时或服务端 5xx 会自动重试一次，并复用完全相同的幂等键。即使第一次请求已经在服务端成功但响应丢失，第二次也会取回已有任务，不会重复冻结或生成。

### 单事件流与批量轮询

应用只维持 `/api/v1/me/tasks/events` 一条账户级 SSE。任务页面不再为每个任务创建一条 EventSource。

SSE 是低延迟路径，批量轮询是可靠兜底：

```text
N 个 waitForTask 调用
        |
        v
共享 taskWaitEntries Map
        |
        +--> 账户级 SSE 按 task.id 分发
        |
        +--> GET /api/v1/tasks?ids=... （每批最多 100）
```

轮询间隔按等待任务数自适应：

| 活跃等待数 | 前台批量轮询间隔      |
| ---------- | --------------------- |
| 1-4        | 调用方间隔，默认 2 秒 |
| 5-20       | 3.5 秒                |
| 21-50      | 5 秒                  |
| 51-100     | 6 秒                  |
| 页面隐藏   | 至少 12 秒            |

连续网络失败采用指数退避，最大 30 秒。收到 SSE 或批量快照后，只有状态、错误、产物 key 或完成时间发生变化才触发业务回调，避免无意义的 Vue 响应式重算。

旧实现等待 100 个任务时会建立约 100 条 SSE，并产生约 50 次单任务请求/秒。新实现保持 1 条 SSE，100 个任务前台约每 6 秒 1 次批量请求，HTTP 请求率降低约 300 倍。

### 页面切换恢复

任务状态的事实来源是服务端数据库，不是页面组件。离开工作台时只停止页面订阅；任务继续在 Worker 中运行。返回页面后从任务列表恢复，文生图和创作工作台最多同时接管 100 个进行中任务，所有等待都复用批量协调器。

任务已经成功但产物 URL 在前端首次读取时缺失，文生图工作台会以 1.5 秒间隔补取，最多 10 次。该补取只针对终态结果，不会重新提交上游任务或重复扣费。

## 后端队列算法

### 突发容量和实际并发

`user_max_running_tasks` 是单用户“运行中 + 排队中”任务总量上限，默认 100。迁移 `00028_user_task_burst_capacity.sql` 只把仍为旧默认值 3 的配置提升到 100，不覆盖管理员已经设置的其他值。

真正访问上游的并发由 `WORKER_CONCURRENCY` 控制，Compose 默认 2。两者必须保持分离：

```text
用户突发提交 <= 100
        |
        v
PostgreSQL 持久任务 + Redis Asynq 队列
        |
        v
Worker 并发窗口（默认 2）
        |
        v
图片上游
```

增加 Worker 实例或并发前，必须确认上游限额、数据库连接池和 R2 上传带宽。不能为了缩短队列直接把 Worker 并发调到 100。

### 幂等和结果回收

- 数据库唯一索引约束 `(user_id, idempotency_key)`。
- 本地 task UUID 同时作为 C2A `client_task_id`。
- Worker 重启、网络重试和延迟恢复继续查询同一上游任务。
- 图片每完成一张就由 `taskOutputCollector` 持久化，部分成功不会因后续网络错误丢失。
- 任务成功状态、原图 keys、缩略图 keys 和费用结算在事务中完成。

对于 C2A 和 CRUN，单轮网络错误先立即重试一次。仍失败且尚无产物时，任务从 `running` 恢复为 `queued`，分别在 15 秒、30 秒后使用同一任务 ID 接管。持久化 attempt 达到 3 后才进入最终失败结算，防止无限恢复。

### 僵尸与丢队列恢复

周期回收每次最多处理 500 条，避免一次扫描长时间占用 Worker：

- `running` 超过 30 分钟：恢复为 queued，使用新 Asynq 记录接管。
- `queued` 超过 10 分钟：先通过 Inspector 检查同一业务任务是否仍有 active、pending、scheduled 或 retry 记录。
- 原任务仍可执行：不重复入队。
- 队列中确实不存在可执行记录：创建带唯一恢复 ID 的补偿任务。

这一检查避免正常长队列中的旧任务每 10 分钟生成一个恢复副本。

## API

批量任务快照：

```http
GET /api/v1/tasks?ids=<uuid>,<uuid>,...
```

- 一次最多 100 个 ID。
- 自动去重，响应保持输入顺序。
- 只返回当前登录用户拥有的任务；不存在或属于其他用户的 ID 被忽略。
- 返回对象与 `GET /api/v1/tasks/:id` 相同，包含缩略图和原图 URL。

## 验证和监控

前端压力测试：

```bash
cd apps/web
npm run test:task-concurrency
```

测试断言：100 个等待器只发出 1 个批量请求；30 个同时提交的峰值网络并发等于 6。

服务端验证：

```bash
cd apps/server
go test ./...
go vet ./...
```

生产监控至少包含：queued/running 数量、队列等待 P50/P95/P99、任务成功率、网络恢复次数、最终失败错误码、上游耗时、R2 持久化失败数。出现大量 queued 时先检查 Worker 和上游容量；出现大量 `upstream_unreachable` 时检查恢复是否成功，不能只扩大浏览器轮询频率。

## 部署

部署必须同时更新 Server、Worker 和 Web，并执行迁移：

```bash
docker compose --env-file .env up -d --build server worker web gateway
```

部署后在后台确认“用户同时任务上限”为预期值。`WORKER_CONCURRENCY` 建议从 2 开始，根据上游 429、队列等待时间和 CPU/内存逐步调整。
