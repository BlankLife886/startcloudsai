模拟生成使用本机HTTP上游和图片存储响应，不产生收费模型调用。每组使用独立临时数据库，正常结束自动清理；停止或中断不算通过。原手工测试账号、订单和模型配置不被这些场景修改。界面会保留最近结果，规则已变化的旧结果会标为「需要重新验证」。

## 常见问题随配置更新

价格页常见问题复用购买弹窗的套餐目录，展示各方案的兑换比例、充值上限、锁价资格、退款窗口、图片并发加成及可用支付方式。查看退款和价格保护问题时，已登录用户还会看到当前选中订阅的购买时规则，区别于在售方案；旧订阅不会被新套餐配置覆盖。

手工测试：打开价格页，在另一个标签页的后台调整自定义充值比例或某个订阅的退款窗口，再返回价格页；套餐和 FAQ 会重新读取配置。分别核对“自定义充值”“额度包锁价”“未使用退款”“额外并发”问题，也可以直接搜索更新后的门槛或套餐名。关闭全退窗口的套餐应显示未启用，不能显示成默认时限；下架自定义充值应显示未上架。读取失败时会提示无法读取当前规则，不用预览方案或默认数字代替。

所有数字计算例子都标明假设，不代表当前套餐报价。自动测试在 `apps/web-react` 执行 `npm run test:pricing-faqs`；页面测试为 `WEB_BASE_URL=http://127.0.0.1:8144 npx playwright test tests/e2e/pricing-faq-data.spec.js --project chromium --workers 1`，使用模拟接口，不修改测试订单或余额。

## 一键测试调价与多用户并发

在原控制台「调价与并发联调测试」点击对应项目的「运行测试」，无需提前购买套餐或修改手工测试账号。一次运行一组；运行中自动显示各项的预期、实测和结果。可以停止，停止或中断不算通过；刷新页面或重启环境后保留最近结果，点击「重新运行」可复测。

| 测试项 | 自动执行与预期 |
| --- | --- |
| 套餐中途调价 | 后台把19.90元套餐改成29.90元，每日额度100改200，并发加成2改4。旧页面提交被拦截；原待支付订单仍付19.90元、发100积分；已订阅用户保留原额度及总并发6；新订单使用29.90元和200积分；旧用户真实执行一次任务扣3积分。 |
| 模型调价与实际消费 | 后台把模型从3积分调至5积分。原锁价用户及已确认报价的排队任务扣3；新订阅、不锁价订阅、普通额度包扣5。先耗完订阅额度，合格额度包继续扣3；升级、退款后重购改为扣5。核对模型HTTP请求和积分批次实际结算。 |
| 多用户对话并发 | 普通用户、图片并发加2订阅、图片并发加4订阅同时提交共24个对话任务，混合助手与画布场景。每人最多4次对话，合计12次；图片额度仍分别为4/6/8。超额排队，取消一个排队任务后其余完成，分别扣15/24/30积分且无冻结残留；订阅图片加成不能绕过对话上限。 |

每次运行创建独立临时数据库并自动清理，不修改当前控制台用户、订单、余额或后台价格配置。模型由本机HTTP/SSE模拟服务响应，不调用付费模型。后台调价、建单、付款回调及用户提交使用正式API处理器；任务通过正式Worker领取和执行逻辑完成冻结、价格保护和结算。并发通过同时保持模型HTTP请求并测量每个账号峰值验证，并非只改任务状态。

覆盖边界：套餐/锁价/对话三组使用对话模型；新增生图场景调用正式图片执行逻辑与本机模拟上游。此控制台不验证真实支付渠道、外部供应商性能、视频生成或Redis队列传输，也不启动完整后台Worker。独立Redis执行池验证仍使用 `node scripts/test-task-chains.mjs --only E-07`。

命令行复测（项目根目录）：

```sh
cd apps/server
GOMAXPROCS=2 GIN_MODE=release go test -p 1 ./internal/worker -run '^TestBillingScenario' -count=1 -v
```

测试失败时展开阅读已显示的错误文本，并查看 `.artifacts/payment-sandbox-8144/sandbox.log`。代码更新后按文末命令原地重启，会重新编译测试程序。

## 自定义充值（当前）

固定额度包和自定义充值由后台分别上架/下架，可同时显示，均使用原套餐卡片。
自定义充值卡片显示「1元起」，点击「自定义金额」后在支付弹窗输入整数金额，最低1元，默认1元100积分。
后台「套餐管理 → 积分包 → 自定义充值 → 编辑」可调整每元积分、锁价开关与最低单笔金额（初始30元）。
配置脚本不会因为开启自定义充值而自动下架固定包，原有订阅及已购权益不受影响。

自定义充值单笔限制为1–1000元的整数金额。支付弹窗输入1应显示100积分，30显示3000积分，1000显示100000积分（按默认兑换比例）；1001、0、负数和小数均不能提交，服务端也会拒绝超额建单。
在控制台模拟付款并回调后检查钱包，重放回调不能重复到账。不同充值金额仍只允许一笔
未支付订单。修改后台规则后，旧订单按原快照到账；新订单按最新比例和门槛。
单笔达标仍需有效且支持额度包锁价的订阅；退款审核或处理中不会恢复锁价。

自动化验证（独立临时数据库，不修改手工测试数据）：
`go test ./internal/httpapi -run 'TestCustomRecharge|TestAdminCustomRecharge' -count=1`（在 apps/server 执行）。

用户端、管理端和模拟支付均从此入口进入。后续更新复用该地址，不另开测试环境。旧测试服务已关闭，旧数据库和日志保留。

这是独立 PostgreSQL 测试库、真实业务 API 和模拟支付渠道的组合。不会真实扣款，不要扫描二维码或使用真实支付账号。原有服务、业务数据库和支付配置不受影响。

订阅新版已接入：控制台使用「订阅测试」账号进入「我的订阅」，测试24小时发放、
同系列升级及退订审核。后台入口为「订阅变更」。完整规则见 [SUBSCRIPTIONS.md](SUBSCRIPTIONS.md)。

合同与额度包锁价配置在「套餐管理」：订阅可配置模型锁价、延伸至合格额度包和额外共享并发；
自定义充值可配置每元积分、是否接受锁价及最低单笔金额，历史固定包保留旧资格。
已有订单及测试余额保留，旧订阅不补造价格合同，需新购或升级测试新合同。
合同价格、双重资格、退款期间停用、旧任务重试与并发在临时数据库自动测试，不调用真实模型。
控制台「模拟使用订阅积分」仍只测订阅消费和退款资格，不代表模型报价或额度包锁价测试。

## 先测试一笔付款

1. 控制台的「支付测试」账号点击「选择套餐」，自动登录用户端。
2. 点击「自定义充值」卡片的「自定义金额」，输入1元，确认显示100积分，再选择支付方式生成待支付订单。
3. 在另一个标签页打开控制台，点击「刷新状态」，找到对应平台订单号。
4. 点击该行「模拟付款并回调」，回到用户端刷新订单和钱包。
5. 默认规则下订单应为已完成，余额增加100积分。点击「重放回调」后余额不应继续增加。

手动测试前先记录控制台余额，以后核对本次增量，不要求已有账号余额为零。更新充值规则未清空历史记录。

## 其他场景

测试订阅积分使用：购买订阅并模拟付款后，在对应测试账号卡片填写积分数量（默认1），
点击「模拟使用订阅积分」。该操作执行实际钱包冻结与结算，不调用模型，也不扣额度包积分。
随后进入该账号「我的订阅」，应显示已使用积分且不可自助退款；后台可从
「订阅变更 → 人工例外退款」按平台订单号协商处理。退订冻结期间不能继续模拟消费。
使用记录会保留，测试按钮不会自动恢复已用积分或退款资格。
新版订阅已改为每24小时重置：消耗部分额度后点「模拟推进一天并发放」，订阅可用额度应回到
套餐单期额度，不与上期相加。钱包显示「周期到期」流水；通用额度包不变。
连续跳过多个周期只保留当前有效额度，订阅结束后本期未用额度失效。旧版自然日测试账号仍按原规则处理。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 待支付订单复用 | 对相同套餐再次发起购买 | 复用同一订单，不重复请求渠道建单 |
| 套餐卡片继续支付 | 建单后关闭弹窗或刷新价格页 | 对应套餐按钮显示「去支付」及剩余时间；点击直接读取原订单展示二维码，不发起新建单；取消或到账后恢复选择按钮 |
| 每人一笔未支付 | 基础包未支付时点击进阶包或订阅的「选择此方案」 | 在选择支付方式之前立即提醒已有订单，显示套餐和金额并提供「查看我的订单」；取消或付款完成后才能换购；待核实与到账确认中也占用该名额 |
| 取消订单 | 用户订单详情取消尚未支付订单 | 渠道关闭，平台显示已取消；刷新或重新登录后保持已取消，余额不变 |
| 渠道已建单但超时 | 控制台选择「渠道已建单，但返回 504」并应用，再购买 | 显示待核实；重复购买不再建单；控制台模拟付款回调后到账 |
| 人工关联渠道单号 | 上述超时场景，进入后台「安全中心 → 支付对账 → 关联渠道单号」 | 输入控制台对应的平台和渠道单号，校验通过后恢复查询；不会新建渠道单 |
| 渠道根本没建单 | 选择「渠道未建单，并返回 504」并应用，再购买 | 待核实且控制台没有渠道记录；后台对话框选择未建单核查，填写说明后结束订单 |
| 付款后回调丢失 | 新订单点击「仅标记已付」，再「运行一批对账」 | 自动补齐到账；再次对账不重复加积分 |
| 过期 | 新订单点击「模拟过期」，用户端刷新状态 | 显示已过期，无积分入账，与已取消独立筛选 |
| 历史积分补发 | 点击「执行一次积分补发」 | 补发测试账号从 100 变为 500；重复执行仍为 500 |
| 续订不同额度 | 查看续订账号，再点击「模拟推进一天并发放」 | 初始 200、当前日额度 100；推进一天后 1,100、当前日额度 900；旧周期不提前按新额度发放 |
| 超过 500 笔历史对账 | 「准备 550 笔历史订单」，连续「运行一批对账」 | 每批最多 100；约 6 批覆盖全部 550 笔，缺渠道单号记录保留为待核查，不会伪造成功 |

异常建单模式仅作用于下一次实际渠道建单，随后恢复正常。已有待处理订单被复用时不会消耗模式。

## 使用边界

- 各测试用户共享当前浏览器的用户会话。切换账号后，旧用户标签页也要刷新；不要同时在不同标签操作不同账号。管理员会话独立。
- 进入用户端或后台使用控制台按钮即可，不需填写密码。会话有效 24 小时。
- 模拟推进同步影响订阅业务时钟、发放及订阅页面，不改变电脑时间和支付二维码有效期。
- 没有运行自动 Worker。补发、对账通过控制台按钮执行真实业务函数，便于控制时机。
- 仅开放支付相关写操作，模型调用和其他管理修改未开放。真实第三方回调网络、真实扫码、退款和发票不在此环境的验收范围。
- 服务断开后重新打开入口即可；重启会从 `session-state.json` 恢复原测试库、账号、时钟和模拟渠道记录，不自动清空数据。

## 启动与自动验证

在项目根目录执行：

```sh
node scripts/payment-sandbox.mjs
```

代码更新后使用 `node scripts/payment-sandbox.mjs --restart` 原地重启，保留原入口和数据。

当前无需再执行。启动要求本机 PostgreSQL 可通过 `postgres://localhost:5432/postgres?sslmode=disable` 连接并建库、Go 和 Node 可用、两个前端依赖已安装，8144/8145/8146 未被其他服务占用。8145/8146 仅为内部前端服务，测试统一使用 8144。检测到已运行的测试环境时直接复用，脚本不接受其他入口端口。

```sh
node scripts/test-payment-sandbox.mjs
```

自动验证固定访问本机沙盒，在支付测试账号追加 5 笔订单和 3,600 积分，不会重置数据；不要与手工购买同时执行。

日志和进程记录：`.artifacts/payment-sandbox-8144/`。不提交该目录中的运行凭据。停止服务时先核对 `processes.json` 中 PID 对应的进程，再仅向这些沙盒进程发送 SIGTERM；停止不会删除数据库。
