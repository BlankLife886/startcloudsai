# 任务执行与资源分配

更新日期：2026-09-09。实现与本地独立验证已完成，详见[验证结果](./TASK_EXECUTION_VALIDATION.md)。尚未部署或向业务数据库执行迁移。

## 统一的范围

各业务保留自己的任务记录、输入和结果展示，共用执行资源的计算与准入规则。`tasks` 和 `assistant_runs` 不合并成一张业务表。

| 入口 | 执行记录 | 配额池 | 计数方式 |
| --- | --- | --- | --- |
| 文生图、图片编辑及普通图片工具 | `tasks` | 生图 | `max(work_units, count, 1)` |
| 无限画布图片节点 | `tasks` | 生图 | 同上 |
| AI 电商及批量图片业务 | `tasks` | 生图 | 每个实际任务的图片工作量累加 |
| AI 助手生图、UI 设计资源生成 | `assistant_runs` | 生图 | 本次 `count` 张；缺少数量的旧生图记录沿用 2 张 |
| AI 助手对话、工具规划、画布 Agent | `assistant_runs` | 对话 | 每个正在执行的 Run 占 1 个名额 |
| 助手专用 PPT/PSD 文件生成 | `assistant_runs` | 对话 | 1 个名额；线路按实际文件服务商计算 |

仅供历史列表展示的 UI 设计图片投影记录，以服务器写入的专用标记排除，避免同一次生成同时计入两张表。

画布 Agent 提出或编排图片方案时使用对话名额；实际图片提交后，图片任务另行占用生图名额。同一会话内保持单个 Run 执行，新任务按队列顺序领取。恢复时，已经提交上游且持有名额的图片任务可先于尚未开始的队列项继续执行，避免队列互相等待。

## 配额与调度

生图和对话分别设置账户上限与全局上限。同一用户从文生图切到画布、再进入助手，正在执行的图片工作量会相加。订阅并发加成用于生图上限。

| 设置 | 含义 | 正常默认值 |
| --- | --- | --- |
| `user_max_concurrent_tasks` | 账户基础生图名额 | 4 张 |
| `global_max_concurrent_tasks` | 全局生图名额 | 保留原设置，缺省为 2000 张 |
| `user_max_concurrent_chats` | 账户对话名额 | 4 个 Run |
| `global_max_concurrent_chats` | 全局对话名额 | 32 个 Run |
| `WORKER_CHAT_CONCURRENCY` | 单个 Worker 的对话执行槽位 | 8 |

图片全局设置无效或非正时，后端兜底为 64；这不覆盖已有正常的后台设置。Worker 执行槽位与业务配额是不同限制：后台上限是最多允许的工作量，并不保证每个进程都同时执行到该数量。

领取任务时，在共享的全局锁、账户锁保护下，检查：

1. 账户正在执行的同类工作量 + 本次工作量 ≤ 账户上限。
2. 全局正在执行的同类工作量 + 本次工作量 ≤ 全局上限。
3. 所选线路正在执行的全部工作量 + 本次工作量 ≤ 线路上限。

对话与生图若使用同一条供应商线路，仍共同受该线路上限约束。专用文件生成也占用其实际服务商线路。

容量只是暂时被占用时，任务等待释放。单个批次本身超过账户、全局或可用单条线路的总容量时，创建接口返回 422，事务回滚，不冻结费用。如果后台在入队后降低容量，或失败切线后剩余线路已容纳不了该批次，Worker 明确结束失败并释放冻结费用，不让任务永久排队。

## 助手多图

一个 Run 生成 4 张图，必须先取得 4 个生图名额；不能只占 1 个名额后在内部并发生成多张。

各图片适配器从统一的工作量函数获取数量，在调用上游前再次验证持久化任务的类型、数量、运行状态、尝试编号及有效租约。对话 Run 不能直接进入图片适配器。

上游支持同提示词批量生成时，沿用一次请求携带数量。独立提示词、逐张参考图，以及要求一图一个 Job 的供应商协议，仍可能产生多个请求；这些请求对应的图片名额必须全部预占，不能成为绕过账户或线路限制的额外并发。

助手显式提交的生图类型不会在 Worker 中因为问候语而自动改成对话。类型与计费在准入前确定；对话内部的工具规划仍属于对话池。

## 执行池与恢复

`assistant-chat` 由独立的对话 Worker 池消费。`assistant-image` 与普通图片任务进入图片侧执行池。旧 `assistant` 队列仍被消费，处理器读取持久化 Run 类型后，将其转投正确的队列。

创建后的 outbox 派发、管理员重排、Worker 启动恢复与租约过期恢复都使用相同的类型选择。队列只负责唤醒，数据库的领取与租约才决定执行权。

对有明确上游任务标识或当前尝试仍在提交/等待中的恢复记录，保留已经占用的名额，不能仅因本地状态改成排队就释放。普通任务优先恢复原尝试轮询；助手有已知图片任务标识时固定原线路，恢复领取时扣除自身已保留的名额，避免重复预占而卡住。助手等待已知任务超时，也不会清空标识后自动切线重新生成。上游未返回任务标识的未知请求仍沿用不确定提交的保护策略，无法据此精确统计远端是否仍在执行。

## 模型、参数与计费绑定

新任务在创建事务内，将模型配置、授权的候选线路和请求参数记录到私有 `execution_snapshots` 表。模型标识、上游模型名称、连接地址、密钥、适配器、超时、模型能力及价格不会随着之后的后台编辑被替换。

候选线路必须满足原工作区授权和价格约束。切线只能在提交时保存的候选集合内进行，不会因为后来新增了模型或开启了跨供应商均衡而扩大候选集合。

新工作准入时，服务是否启用、维护状态及并发上限仍读取实时控制。已经提交上游并取得任务标识的任务，恢复时继续使用原连接快照和已保留名额；后台降低上限或暂停新任务，不会让既有任务因为重新申请自己的名额而卡住。

已有旧记录在首次执行时补齐绑定；遗留环境变量/旧服务配置路径在首次实际调用时加密保存连接，后续重试复用。新迁移不会追溯推断旧任务当年使用的配置。

用户提交 A 模型任务后，在界面选择 B 只影响后续提交。排队消息仍允许显式编辑提示词，但不会随之修改该 Run 的模型、图片数量或计费绑定。显式重试已失败的助手 Run 会清除上一轮的线路失败标记，重新尝试原快照内的候选；它与中断恢复、自动切线分开处理。

执行快照不会合并进公开的任务参数、助手消息或 API 输出。快照禁止更新，关联业务任务删除时同步清理。

## 界面与管理指标

助手配置返回账户生图/对话占用及批次数量上限，每个图片模型还返回自己的批次上限。Web 和 Flutter 的数量选择使用账户、全局、线路、模型能力共同限制后的数量。

用户额度、订阅权益和后台设置分别标明生图与对话。管理台系统指标新增 `executionPools` 展示跨入口的真实占用；供应商线路指标同时包含普通任务与助手。原 `taskPressure` 保留普通任务积压口径，避免把排队记录数与执行名额混用。
