## 当前规则

登录用户在 `/invite` 获取专属链接 `/auth?ref=<16位邀请码>`。只在首次邮箱验证创建账号的事务中绑定邀请人；已有账号登录不会新增或更换邀请关系。无效邀请码不阻止正常注册，但不产生邀请关系。

网页打开邀请注册页后，会校验邀请码并保存30天的签名HttpOnly Cookie，离开注册页后在同一浏览器继续注册仍可恢复。邀请码本身不是30天后失效，30天是本浏览器归因记录的保留期。再次打开有效邀请链接或手动确认其他邀请码，将替换本浏览器尚未注册的归因记录。跨设备不做隐式追踪，用户可复制邀请码并在另一设备注册页手动输入。

注册页会显示有效、无效、活动关闭、已有账号等状态，可以选择“不使用邀请”。提交注册时明确输入的邀请码优先，其次使用已验证的Cookie；`skipReferral=true`显式跳过两者。注册或登录成功后清除归因Cookie，并通过响应与提示说明最终是否绑定。校验接口按IP限流。

有效邀请链接写入Cookie后移除URL中已消费的ref，换码不再被旧URL覆盖。选择“不使用邀请”立即在注册请求中使用skipReferral，并以URL参数`skipReferral=1`保留当前页面及刷新的选择；这个标记不等于服务端Cookie已经清除成功，清除失败会单独提示。用户重新明确选择邀请码时可撤销跳过。邀请预览最多等待5秒，挂起、超时或失败不能禁用正常邮箱认证，最终归因由注册接口判断。

绑定对象必须是已存在且有效的普通用户，不能邀请自己。邀请码不含邮箱；邀请列表不返回好友邮箱、登录凭证或完整个人资料。

保留后台历史路由 `/admin/referrals`：活动开关、按比例/固定积分互斥模式。当前默认关闭，比例10%、固定值10积分；选择的模式决定恢复后的计提规则，另一数值只作为切换后预设保存。

后台规则包含：最低实付金额、每位邀请人每日计提上限、每位好友仅计提一次正积分奖励。缺省最低实付1元、日上限1000积分、仅奖励一次关闭；旧配置未保存新字段时也使用这些缺省值，部署前必须在规则页确认运营政策。门槛和日上限均允许设置0表示不限制。月结版响应标记`version:3`、`settlementCycle:monthly`；结算周期统一按月，不开放即时到账选项。新后台连接旧API时禁止保存，防止旧服务忽略月结规则却返回成功。

日上限按北京时间的自然日累计计提积分计算，不是在月度到账日重新套用日上限。接近上限时只计提剩余额度，已达上限则保存未计提原因，不在次日补发；取消待结算或冲正到账奖励都不恢复原日额度。每位好友仅奖励一次在首次计提正积分时占用次数，低于门槛等零奖励记录不占次数，取消/冲正也不恢复次数。并发核算在邀请人钱包锁内完成。

返利计提条件：蓝鲸支付经过服务端验证的充值积分包订单首次完成。按比例时仅以订单 `grant_cents` 为基数，不含 `bonus_cents`，向下取整；固定模式对每笔符合条件的充值计提配置积分。零元、零基础积分、注册赠送、兑换码、订阅订单及每日额度不计提。未经支付证明的人工完成订单不计提返利。

返利使用平台确认充值时的配置，在 `referral_rewards` 保存模式、比例或固定值、基数和结果；月底结算不按最新规则重算。关闭活动停止新绑定和新计提，不取消已确认的待结算权益；是否继续发放由独立的`settlementPaused`决定。当前整体停用时该开关为true，自动月结暂停，恢复后才处理保留的待结算记录。再次开启不会追补停用期间未计提的历史订单。

第二版同时保存完整规则快照，以及活动关闭、低于门槛、日额度不足、好友已获奖、存在待追回奖励、向下取整为零等决策原因。尚未具备邀请关系或邀请人/好友已停用时不发奖。后台可按邮箱、用户ID、订单号查询，并按奖励状态筛选。

## 一致性

邀请关系以invitee_id唯一，计提记录以order_id唯一；计提与好友订单完成在同一事务，不增加邀请人的可用余额。重复回调和并发对账不能重复计提。

## 月底结算

- 以平台确认并记录计提的北京时间自然月归属。例：9月1日至9月30日的计提，10月1日00:05起统一到账。迟到回调按实际确认记账月份归属，不回写已结月份。
- 计提归属、关账判断与结算时间均来自数据库clock_timestamp，不使用Worker机器的时钟判断月末，公开业务函数也不接受调用者提供的未来结算时间。
- 每位邀请人每月一张 `referral_settlements` 结算记录，汇总当月所有未取消的待结算积分；每月一次钱包入账，账本键为 `grant/referral_settlement/<settlement_id>`。
- Worker每分钟扫描到期月份，每轮最多处理50个用户月份、总预算45秒。不是只在1日运行一次，因此停机错过时点后可以补结算，批量较大时分轮完成。
- 结算记录、普通积分钱包入账、关联奖励状态变更同事务，月记录唯一约束与钱包锁防止多Worker重复到账。
- 结算失败保留待结算并延后15分钟重试；后台显示异常提示。不吞掉失败或将失败标为到账。
- 若月份已存在结算批次却仍出现待结算记录，判定为独立账务异常，停止该组的自动发放并提示人工核对，不重新生成第二笔月结。人工修复前不得随意清除暂停标记或改写已结批次。
- 邀请人已停用或有待追回奖励时暂停该人的结算，待条件解除后再自动处理，既有待结算不直接作废。
- 历史即时到账记录保持原状，不转回待结算，也不重复入账；仍可使用原单笔账本键核对和冲正。

待结算金额不是可用余额。用户页面分别显示待结算、累计净到账、已追回和待追回。后台支持按归属月份筛选，并查看月结批次和真实到账时间。

00:05是开始处理时间，不是全量用户的同时到账承诺。当前每分钟每轮最多50个用户月份，单执行链理论最多每小时3000组，实际还取决于数据库耗时和锁竞争。扩大推广前需要按真实账号规模进行补结吞吐和到账时长验收。

本功能不是提现或多级分销，不存在二级邀请奖励。邀请返利不会自身再次触发返利。

## 冲正与对账

奖励状态：`pending_settlement`待结算、`granted`已到账、`skipped`未计提、`voided`已取消待结算、`recovery_pending`待追回、`reversed`已冲正。累计到账不包含待结算或已取消金额，并扣除已冲正部分。

结算前取消奖励只转为voided，保留金额、依据和操作者记录，不扣钱包、不调用支付退款。结算后才通过原有冲正逻辑追回对应订单的奖励份额。接口要求expectedStatus：如果取消与月结并发，锁内发现已到账会返回409，必须刷新并重新确认扣款，不能把取消悄悄升级成扣款。

管理员在“返利与对账”中核对原始奖励账本与冲正账本，填写6-300字核查依据并明确确认后，才能追回该笔奖励。只动用邀请人的普通可用积分，不使用体验积分、冻结积分或订阅额度；只允许整笔追回。余额不足不扣成负数，改为待追回并暂停此邀请人的后续新返利；已有余额不会被自动冻结。余额恢复后由管理员点击“重试追回”，不是后台自动追债。

冲正使用唯一账本键 `admin_adjust/admin/referral-reversal/<order_id>`，与奖励状态和操作记录同事务。重复提交不重复扣款。月结奖励核验结算批次账本及该批次的奖励分配；旧即时奖励核验原单笔账本。原始奖励账本缺失、金额/归属不符，或冲正账本与状态不一致时拒绝操作，需要人工调查。后台“账本一致”仅检查邀请奖发放/冲正记录，不代表已向支付渠道完成财务对账。

独立操作表保存发起与完成的管理员及依据，原奖励和规则快照不改写、不删除。这是返利冲正能力，不是支付退款能力，不会向蓝鲸支付发起退款，也不会改变好友原充值订单状态。当前充值积分包尚无自动退款回调接入；未来退款流程必须明确调用并处理待追回结果，不能仅凭此页面宣称完整退款闭环已上线。

## API

- `GET /api/v1/me/referrals?page=1`：登录用户专属链接、当前规则、总邀请数、已充值好友数、累计奖励和每页20条奖励记录。`hasMore`用于翻页。
- `POST /api/v1/auth/session`：新增可选`referralCode`，仅首次注册消费该字段。
- `GET/POST/DELETE /api/v1/referral-attribution`：读取、校验并保留、清除当前浏览器归因；POST字段为`code`。
- `GET/PUT /api/v1/admin/referral-config`：独立管理员鉴权和现有写审计；字段`enabled`、`mode`、`percent`、`fixedPoints`、`minimumAmountCents`（人民币分）、`dailyLimitPoints`、`firstRewardOnly`。
- `GET /api/v1/admin/referral-relations?q=&page=1`：邀请关系与可追溯充值/奖励统计。
- `GET /api/v1/admin/referral-rewards?q=&status=&month=YYYY-MM&page=1`：奖励记录、月份/批次/到账时间、规则快照、账本一致性及全局汇总。
- `GET /api/v1/admin/referral-rewards/{orderId}/actions`：该奖励的冲正操作记录。
- `POST /api/v1/admin/referral-rewards/{orderId}/reversal`：字段`reason`、`confirmed:true`、`expectedStatus`；返回`voided`、`reversed`或`recovery_pending`，重复请求安全。

列表每页20条，`hasMore`表示存在下一页。统计只覆盖已产生的邀请返利决策记录，旧版活动关闭期间没有生成记录的订单不会自动补齐。

## 上线与运营边界

迁移00126建立邀请三张表；00132新增规则快照、状态、冲正字段和操作表；00133新增月度计提和结算批次，不直接增减已有余额。邀请控制迁移原编号00131与独立订阅迁移重号，因尚未应用而调整为00132，订阅文件保持不变。若其他环境曾应用旧编号，必须先核对迁移历史，不能直接重命名已应用版本。

发布流程应先在隔离测试库验证，再协调部署API、Worker与前端；先停止旧写入进程，禁止新旧即时/月结版本混跑。数据库要求已到账状态必须有到账时间，阻止旧代码插入新的即时奖励。存在待结算、已取消或结算批次时，降级迁移会拒绝丢弃月结信息。本地迁移实际状态以上方最新核查记录为准，本轮未做迁移或重启。当前注册IP限制与邮箱规范化不能完全阻止同一人控制多个真实邮箱，公网仍需异常支付审查和成本监控。

初期建议由运营审核大额/高频异常账号。仅奖励一次开关默认关闭，开启后也不等于“首次充值”：未达门槛等未计提的历史充值不占次数。首次正积分计提即占用次数，月底才入账。

上一版测试覆盖比例向下取整、固定模式、并发重复支付、赠送积分排除、自邀/覆盖关系及未验证订单不返利。第二版新增Cookie篡改/过期、跨好友并发日上限、门槛和仅奖励一次、余额不足待追回及重复冲正、注册页归因恢复/主动清除等用例，尚未执行。详细待测步骤见 `REFERRAL_TEST_CHECKLIST.md`。
