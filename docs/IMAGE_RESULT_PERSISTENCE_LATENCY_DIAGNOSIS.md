# 批量图片任务结果回收延迟诊断

> 状态：诊断结论，尚未修改服务端实现  
> 记录日期：2026-08-13  
> 适用现象：1–4 张图片生成速度正常，但同时执行约 20 个任务时，用户端看到图片通常需要 2 分钟以上；上游约 50 秒时已经完成生成。

## 结论

从当前代码链路看，最可能的问题不是前端，也不是普通任务排队，而是：

> 上游完成后的“结果下载 + 图片处理 + 对象存储 + 数据库落库”在同一批任务中按任务串行执行。

这会导致 1–4 张时正常，20 个任务时尾部图片明显延迟。对象存储慢会放大问题，但根因是结果回收架构把存储、缩略图和数据库操作串在轮询响应解析里。

## 代码证据

1. 同一路由一次聚合轮询最多处理 20 个任务：`apps/server/internal/worker/worker.go:1600`。

2. 轮询响应使用流式 JSON 逐个解析任务，但每解析一个任务后，会同步执行图片提取和完成回调，完成前不会继续解析下一个任务：`apps/server/internal/c2a/client.go:621`。

3. 如果上游返回图片 URL，还会逐张下载并转成 Base64：`apps/server/internal/c2a/client.go:314`。

4. 每个任务之后还要执行：

   - Base64 解码
   - 图片尺寸读取
   - 内存信号量等待
   - 生成 JPEG 缩略图
   - 原图上传 R2
   - 缩略图上传 R2
   - 更新任务部分结果
   - 发布 `image-ready` 事件

   完整流程位于 `apps/server/internal/worker/task_outputs.go:78`。

5. 单张图片的原图和缩略图上传是并行的，但不同任务之间仍然串行。只有当前任务完成 `completePolledImageTask` 后，轮询器才会继续处理下一个任务：`apps/server/internal/worker/worker.go:1670`。

假设每个任务的下载、缩略图和上传平均增加 3–5 秒，20 个任务尾部就会增加约 60–100 秒。加上上游 50 多秒，正好落入 2 分钟以上。

## 队列影响

当前迁移后的默认配置是：

- 单用户上游在途：20
- 全局上游在途：2000
- Worker 并发：32
- 图片轮询器：默认最多 4

因此，如果 20 个上游任务在 50 秒左右都已创建并完成，普通生成队列不是主要原因。

轮询间隔只有约 2–4 秒，也无法单独解释额外一分钟。真正的问题是轮询器发现结果后，被下载和转存操作持续占用。

## 存储影响

R2 可能是放大因素，但不能简单归类为“R2 慢”：

- R2 单次上传没有独立超时控制。
- 每张图需要上传原图和缩略图。
- 缩略图生成是 CPU 操作。
- 大图会等待 `imageMemory` 信号量。
- 上游 URL 下载也在关键路径中。

所以准确说法是：结果持久化流水线串行，存储延迟、图片尺寸和缩略图 CPU 共同放大了尾部延迟。

## 线上确认方式

Worker 已有以下日志：

```text
task <id> stage=image_persist duration_ms=<耗时>
```

统计同一批 20 个任务的 `image_persist duration_ms`。如果这些耗时相加接近额外的 60–100 秒，就能直接确认。

同时对比以下日志：

```text
task <id> claimed ... queue_wait_ms=...
task <id> submitted asynchronously ...
task <id> stage=image_persist duration_ms=...
```

当前后台“耗时”只是 `startedAt → finishedAt`，把上游生成、轮询、下载、缩略图、R2 和落库全部混在一起：`apps/admin/src/views/TasksView.vue:232`。因此后台现有页面无法直接判断慢在哪。

## 优化方向

建议按以下优先级实施：

1. 将聚合轮询的结果解析与持久化分离。
2. 增加受控的结果持久化工作池，例如同一路由并发处理 4–8 个已完成任务。
3. 继续使用现有图片内存信号量限制内存，不能无上限并行。
4. 增加 `upstream_ready_at`、`persist_started_at`、`persist_finished_at` 指标。
5. 后续可考虑原图先交付、缩略图异步生成，进一步缩短首图可见时间。

## 实施边界

本报告仅记录诊断结论和后续验证方案，目前没有修改服务端结果回收、对象存储、图片处理或队列代码。实施优化前应先用同一批线上任务日志确认各阶段耗时，并以受控并发和现有内存信号量为边界设计持久化工作池。
